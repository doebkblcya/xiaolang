# QQ 官方接口能力核对与修复清单

核对日期：2026-10-23（北京时间）。项目基线：`6f0c2fd`；当前使用 `@tencent-connect/qqbot-nodejs 1.0.5`。

本次对照当前 QQ 官方网站能力目录、167 个接口／事件／协议文档页面、已安装 SDK 源码和小狼实现。未发送 QQ 消息、调用真实模型或执行群管理操作，未核验当前 AppID 的全部权限。核对时此前暂停的本地改动尚未提交或部署；当前实施结果见第 7 节。

结论：现有群聊／单聊的文字收发、图片理解、发送回执和持久化已经工作，但消息内容和平台元数据没有完整映射。下面列出 **12 项基础接入修复／补充、3 项聊天页面补充**；官方其他能力作为独立扩展目录，不自动纳入本轮开发。

逐项参考：[官方接口核对索引](QQ官方接口核对索引.md)，包含 47 个生成 HTTP 接口入口、22 个生成事件入口以及频道／协议参考页面。这些是目录入口数量，不是机器人已获授权的能力数量。

## 1. 官方能力全景与当前覆盖

| 群只读信息 | 群基本信息、机器人群内状态、成员列表与详情 | 只缓存群名；部分接口需要白名单／内邀 | R11；其他资料按需增加，失败不阻断聊天 |

## 2. 基础接入：最终添加／修复清单

### 第一批：消息接收、保存和理解

| 编号 | 已核实的缺口 | 需要添加／修复 | 完成后的行为 |
| --- | --- | --- | --- |
| R01 | QQ 接收引用有 `ref_msg_idx`／`msg_elements`；发送响应也可能提供 `ext_info.ref_idx`。适配器均未保留；内部引用只有 ID | 保存入站／出站引用索引及关系；复用 SDK 引用能力，补充同会话持久化索引与内容映射；先用推送的引用内容，再按已有索引查本地记录 | 面板和模型共用引用内容；引用小狼自己的回复也能关联；找不到就明确原文不可用，不拿普通消息 ID 假装引用索引 |
| R02 | 当前只生成对小狼的提及段，未完整映射其他人／全体成员 | 保留提及对象、可用昵称和“全体”语义；结合正文占位保持位置；区分 AppID 与机器人在群内的 OpenID | 模型和后台知道消息在对谁说；@别人、@全体不被误当 @小狼。原始正文中可能已有 `<@…>`，这里是补结构与身份映射，不是声称文字全丢失 |
| R03 | 顶层 `content`／`attachments` 之外的 `msg_elements` 不处理；官方定义 101／102／103 及递归结构 | 增加有深度、数量、长度限制的递归归一化；保存子消息作者、顺序、类型和内容；区分引用、转发／聊天记录和当前发言 | 组合消息不退化成空白或只有一行摘要；转发内容属于资料，不赋予其中作者当前操作权限 |
| R04 | `message_type=3` 的 `ark_data` 未解析，安装版 SDK 的顶层类型也没有完整声明该字段，但 `raw` 仍可读 | 通过 QQ 适配层读取并归一化卡片类型、提示、标题、描述、来源、链接及可用结构字段；有边界地兼容未知类型 | 分享链接、小程序、位置、名片等至少保留可读内容和类型；不把任意原始 JSON 直接塞给模型，不因卡片存在就自动访问链接 |
| R05 | 附件里的 `asr_refer_text`／`voice_wav_url` 未映射，语音统一是不支持 | 保留语音元数据和 QQ 已提供的参考转写；标注“语音转写”；与顶层正文去重 | 已有转写可供模型和面板读取；没有转写就明确缺失，本轮不额外建设语音识别服务 |
| R06 | 图片仅保留 URL／MIME；其他附件只剩类型名，丢失文件名、大小等 | 统一附件摘要结构，保留官方实际提供的类型、文件名、尺寸／大小、链接；未实现理解的附件也显示占位。为未知消息类型记录有界诊断 | 图片、视频、文件在后台可辨认；“收到附件”和“已理解附件”分开，不自动下载所有文件，不声称视频已看过 |
| R07 | 未保留消息类型、`msg_idx`、可用 `msg_seq`、事件来源及作者补充字段；去重键只有会话＋消息 ID | 使用平台元数据白名单，保存实际收到的索引／序号／事件信息和可用身份资料；核实重投与多元素消息的去重规则；兼容已有消息键和删除标记 | 重投不重复回复，不把不同消息错误合并；引用索引可追溯。字段缺失这一点已确认，实际是否误去重需样本核实，不能现在断言线上已丢消息 |

消息字段依据：[单聊事件](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/c2c_message_create.html)、[群 @ 事件](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/group_at_message_create.html)、[群全量事件](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/group_message_create.html)、[结构化卡片](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/type/ark.html)。

### 第二批：发送、回执和平台状态

| 编号 | 已核实的缺口 | 需要添加／修复 | 完成后的行为 |
| --- | --- | --- | --- |
| R08 | SDK 的非 2xx 分支能解析业务码，小狼常统一丢成 `qq_api_rejected`；SDK 2xx 分支直接返回 JSON，未统一检查业务错误；TraceID 未保留在结构化结果 | 统一提取 HTTP 状态、`code`／`err_code`、安全错误分类和追踪 ID；补 SDK 响应适配，区分明确拒绝与结果未知；凭证失败也保留安全错误码 | 能区分过期、次数超限、禁言、权限、频控、内容审核等原因；收到明确业务失败不误标为“可能发送成功”；不输出密钥或完整上游正文 |
| R09 | 私聊原生流式同时设置 `event_id: message.id` 和 `msg_id: message.id`，官方要求二选一 | 消息回复仅传 `msg_id`；事件回复只用实际事件 ID；不同标识分开保存 | 请求符合协议，避免依赖平台容忍错误参数。当前能发送不证明这个参数组合正确 |
| R10 | 普通私聊和群聊都按 5 次／5 分钟处理；私聊流式也固定 5 分钟；忽略流式响应 `remain_msg_len` | 按场景声明能力和限制；普通单聊次数与群聊分开；文档冲突的私聊有效期保守配置并待小范围确认；处理原生流式剩余长度和结束状态；明确区分本地保守字数策略与平台硬限制 | 不发出明知超额的分段；超长回复和剩余额度可解释；保持“不把被动回复失败升级为主动推送”和“结果未知不盲目重发” |
| R11 | SDK 能转发原始关系事件，小狼只监听普通消息及连接事件；本地配置的 `groupMessages` 不等同平台真实设置 | 接入好友／群关系和主动推送开关事件；保存事件时间与已知状态，提供可选只读查询。群内状态接口有权限才读取并缓存，未授权显示未知 | 能说明已退群／被删好友／主动消息被关闭；已知禁止的提醒不反复尝试。WebSocket 在线、能收到消息、能主动发消息分别展示；不把关闭主动推送等同关闭被动回复 |
| R12 | 适配器正式 API 仍指定 `api.sgroup.qq.com`，SDK Token 默认 `bots.qq.com`；官方现行统一入口为 `api.bot.qq.com` | 统一配置生产 API 与 Token 入口，保留有证据的兼容及沙箱配置；记录明确兼容策略 | 跟随现行平台入口，避免隐式依赖旧域名。这里只确认配置落后，不声称旧域名已经失效 |

## 3. 聊天记录页：补齐后台可观察信息

## 5. 需要保留的边界和待确认项

1. **文档存在矛盾。** 单聊发送页头和收发概述写 60 分钟／4 次，但同一发送页 `msg_id` 参数仍写 5 分钟。因此“按场景拆分”是明确修复，直接把线上私聊放宽为 60 分钟还不是本次核实能保证的结论。群聊页明确为 5 分钟／5 次。消息类型总表也有前后不一致的旧枚举，发送扩展应以当前具体接口和有效权限为准。
2. **权限存在不等于当前账号获权。** 群信息／状态接口有白名单限制；部分群成员能力明确是内邀。查不到应展示未知，不能声称机器人已具备全部接收／管理能力，也不应因为接口无权阻断其他功能。
3. **身份和索引不可互换。** AppID、用户／群成员 OpenID、平台消息 ID、引用索引、外层事件 ID、网关序号及本地 seq 分别保存其用途。官方提供的 union 字段也可能为空，不自动跨群／跨平台合并身份。
4. **引用不保证总有完整原文。** 当前官方事件结构确认能携带内容和嵌套附件，但具体历史事件下发多少仍取决于实际推送。本地没收到或没保存的内容不能编造。
5. **旧数据无法保证补齐。** 未保存的引用索引、语音转写、卡片结构可能无法恢复。本次核查未找到 QQ 群／单聊可任意回拉全部历史消息的通用接口，不能借用频道接口承诺恢复所有旧聊天。
6. **去重缺口与实际丢消息分开。** 本地确实未保存官方建议核对的索引／序号，但不能仅凭这点推断已经发生误去重。修改键时要兼容现有聊天关联和删除标记。
7. **平台推送不保证到达。** 接收全量消息仍受平台设置、权限、在线状态和断线恢复范围影响；原始事件里没有收到的内容，不属于解析器能补齐的范围。
8. **已有 SDK 功能继续复用。** Token、连接、恢复、基础 REST 和引用解析优先复用；安装版 SDK 的类型不全时只在适配器补读取。SDK 的业务错误／空响应等缺口，应通过明确的补丁或适配解决，不默认安装最新版就能修好，也不重造一套 SDK。

## 6. 插件边界与实施顺序

QQ 适配插件负责平台字段、标识和协议；宿主消息契约保留跨平台通用内容；存储负责持久消息和引用关联；触发插件记录实际决定及批次；记忆插件提供已有图片描述；统一日志保存处理事件。面板只通过这些服务读取和展示，不自行解析 QQ 原始包或直接跨插件查表。

建议实施顺序：

1. R01～R07：先修消息接收、归一化、保存及模型输入，保证内容到得了业务层。
2. R08～R12：再修响应语义、流式参数、场景限制和关系状态，保证结果解释准确。
3. R13～R15：最后把真实数据接到聊天页，保留现有 QQ 式布局。

上述内容记录核对阶段的待办和边界，当前实施结果见第 7 节。
